# AI Passport 特斯拉钥匙卡片

本功能目标是在 ESP32-C3 AI Passport 上实现独立运行的 BLE 虚拟钥匙。日常解锁流程不依赖手机。

## 信任与授权模型

1. 用户输入 17 位 VIN，并可自定义显示车型。车型名称只是用户资料，不是车辆身份凭证。
2. 固件规范化 VIN，并根据 SHA-1(VIN) 的前 8 个字节计算 Tesla BLE 广播名称。扫描匹配仅用于发现目标，不代表车辆已通过身份认证。
3. 设备自行生成 P-256 密钥对。私钥必须留在设备内，不得写入日志、导出到二维码或发送给配套服务。
4. 通过 Tesla 支持的车辆授权流程添加公钥。车主按车辆提示使用已有授权钥匙卡/钥匙扣，并在车辆屏幕上确认添加。
5. 只有授权成功后，固件才能建立经过认证的会话并发送受支持的本地 BLE 命令。

蓝牙 MAC 地址只是临时无线电元数据，可能变化；不得将它作为长期车辆身份或钥匙授权成功的证据。

## 板卡限制

当前板卡为 ESP32-C3、8MB Flash、无 PSRAM，配备 ST7789P3 240x320 屏幕和三键 ADC 梯形按键。板载 NTAG213 是无源标签，现有 BSP 没有连接到 MCU 的 NFC 读卡器，因此不能读取、复制或模拟 Tesla 原厂钥匙卡。原厂卡授权仍需在车辆旁实体操作。

现有 BLE Demo 是不可连接的外设广播示例。本功能需要启用 NimBLE central/observer、扫描器、GATT client、有界 worker task，并在页面退出时释放无线资源。板卡当前配置仅允许一个 BLE 连接，RAM 余量有限，扫描和协议缓冲区必须有明确上限。

## 安全要求

- 除非用户明确选择保存，否则不要持久化或记录 VIN。
- 必须评估 ESP-IDF 安全存储方案来保护私钥。Flash/NVS 加密与 Secure Boot 配置是独立要求；没有安全元件时不得宣称具备硬件隔离密钥能力。
- 不能仅凭广播匹配或 MAC 地址显示“已绑定”。
- VIN 无效、签名验证失败、会话数据过期/重放、GATT 错误或授权未完成时必须拒绝执行。
- 解锁必须由用户明确触发；不得扫描到车辆就自动解锁。
- 不得在源码中嵌入 Tesla 账户 token、私钥或凭据。

## 当前实现范围

当前代码提供 VIN 规范化、BLE 广播名称格式化，以及纯逻辑的车辆授权状态机。状态机拒绝乱序事件，只有在收到“需要刷卡”后再收到车辆确认事件，才能进入 AUTHORIZED。主机测试已接入 `tools/validate.sh`，但当前开发环境尚未实际运行。BLE 扫描、密钥生成/存储、Tesla protobuf 通信、车辆授权流程集成及锁车/解锁仍未实现，后续必须分阶段完成协议、内存和真机验证。
